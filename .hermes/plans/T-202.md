# T-202 — Deterministic seed orchestrator

## Goal and scope

Add a production-like local seed command that composes the existing topology generator and field filler, persists valid chains through Drizzle in foreign-key order, and prints a concise report. The command must support:

```bash
pnpm seed
pnpm seed --count 200
pnpm seed --seed 42
pnpm seed --shape linear
```

The default run creates 50 chains and at least 500 `lancamento` rows. A supplied seed must reproduce the same logical data on a freshly migrated database. Without `--seed`, the entrypoint generates and reports a random seed so the run can be replayed. When `--shape` is omitted, chain shapes are selected deterministically with weights of 10% linear, 60% branching, and 30% merge.

In scope:

- deterministic batch construction from `generateChainTopology` and `fillFields`;
- Drizzle inserts for the tables listed in T-202;
- three synthetic CRIs and the existing stable `lancamento_tipo` IDs;
- CLI parsing, validation, package scripts, timing, and final statistics;
- unit and database-backed integration coverage in `scripts/seed/__tests__/seed.test.ts`.

Out of scope:

- changing the topology generator, field filler, migrations, or schema;
- persisting `FilledPessoa.cpfCnpj` or `tipo` (the `pessoa` table only accepts `nome`);
- destructive cleanup of an already populated database or making the command idempotent;
- audit-log rows, soft-deleted fixtures, or production/remote D1 seeding.

## Fixed design decisions

- Use ten topology launches per chain (`LANCAMENTOS_PER_CHAIN = 10`). The default therefore has at least 500 launches; the writer reports the actual inserted count and treats fewer than `count * 10` as an error.
- Derive every chain seed from the user-visible run seed and the zero-based chain index. Shape selection and topology generation must not depend on database IDs, current time, iteration over unordered objects, or `Math.random`.
- Keep generation separate from persistence. Tests can compare generated batches without touching a database, while the database-backed test verifies foreign keys and stored values.
- Insert each chain in dependency order and retain `Map<topologyId, databaseId>` maps for documentos, pessoas, imoveis, lancamentos, and origens. Never infer a generated database ID from insertion order.
- Seed CRIs as IDs 1–3 on a fresh local test database and assign them round-robin by chain index. Before inserting chain data, fail with a clear message if any of those IDs already belongs to a different CRI; do not silently overwrite user data.
- Use `lancamento_tipo` IDs `1 = registro`, `2 = averbacao`, and `3 = inicio_matricula`; verify the lookup rows once before chain inserts.
- Insert no soft-delete or audit-delete value. Omitted nullable columns remain `NULL`, including every `deletedAt`/delete-operation column.

## Subtask 1 — Build the deterministic orchestration layer

**Files**

- Create `scripts/seed/seed-orchestrator.ts`.
- Create `scripts/seed/__tests__/seed.test.ts` with the generation and argument-parsing test sections; later subtasks extend the same file.

**Implementation**

Import the existing generator and filler directly:

```ts
import {
  generateChainTopology,
  type TopologyGraph,
} from "./chain-topology";
import { fillFields, type FilledChain } from "./field-filler";
```

Export the following public surface:

```ts
export const DEFAULT_CHAIN_COUNT = 50;
export const LANCAMENTOS_PER_CHAIN = 10;

export type SeedShape = "linear" | "branching" | "merge";

export interface SeedOptions {
  count: number;
  seed: string;
  shape?: SeedShape;
}

export interface GeneratedSeedChain {
  index: number;
  seed: string;
  shape: SeedShape;
  topology: TopologyGraph;
  filled: FilledChain;
}

export function parseSeedArgs(
  argv: readonly string[],
  randomSeed?: () => string,
): SeedOptions;

export function deriveChainSeed(runSeed: string, index: number): string;

export function chooseShape(runSeed: string, index: number): SeedShape;

export function generateSeedChains(
  options: SeedOptions,
): GeneratedSeedChain[];
```

Implementation details:

1. Parse both `--count 200`/`--count=200`, `--seed 42`/`--seed=42`, and `--shape linear`/`--shape=linear`. Reject unknown flags, missing values, non-integer or non-positive counts, and shapes outside the three-value union.
2. The default `randomSeed` uses `crypto.randomUUID()`; injecting it makes the no-seed behavior testable. Normalize all explicit seed values to strings and print/use the generated value unchanged.
3. Implement a small stable string-to-32-bit hash inside this file, then use it to derive `"<run seed>:chain:<index>"` and a reproducible `[0, 1)` shape roll. Do not import a second random-number package. Map rolls `< 0.10` to linear, `< 0.70` to branching, and the rest to merge.
4. If `options.shape` exists, use it for every chain. Otherwise call `chooseShape`. Generate exactly `options.count` chains with:

   ```ts
   const topology = generateChainTopology(
     chainSeed,
     LANCAMENTOS_PER_CHAIN,
     { shape },
   );
   const filled = fillFields(topology, chainSeed);
   ```

5. Assert that the generator returns unique `chainId` values for the batch and that every filled result refers to the same chain as its topology. Surface failures before any database write.

**Acceptance tests**

Add tests proving that equal options produce deeply equal generated batches; different seeds change the batch; forced shapes apply to every chain; a sufficiently large deterministic sample follows the exact threshold logic; defaults and all supported CLI syntaxes parse correctly; and invalid inputs fail with actionable messages.

```bash
pnpm --dir scripts/seed test -- seed.test.ts
```

This subtask is limited to one new module and one focused test section and should fit within 15–20 implementation turns.

## Subtask 2 — Persist a generated batch through Drizzle

**Files**

- Create `scripts/seed/seed-writer.ts`.
- Extend `scripts/seed/__tests__/seed.test.ts` with writer tests using a freshly migrated temporary/local test database.

**Imports and public surface**

Use the API database singleton only as the entrypoint default; accept it as a parameter so tests can provide an isolated database:

```ts
import { db } from "../../packages/api/src/db";
import {
  cri,
  documento,
  imovel,
  imovelDocumento,
  lancamento,
  lancamentoPessoa,
  lancamentoTipo,
  origem,
  origemFimCadeia,
  pessoa,
} from "../../packages/api/drizzle/schema";
import type { GeneratedSeedChain, SeedShape } from "./seed-orchestrator";

export type SeedDatabase = typeof db;

export interface SeedReport {
  seed: string;
  requestedChains: number;
  inserted: {
    cris: number;
    chains: number;
    documentos: number;
    pessoas: number;
    imoveis: number;
    lancamentos: number;
    lancamentoPessoas: number;
    origens: number;
    finsCadeia: number;
    imovelDocumentos: number;
  };
  shapes: Record<SeedShape, number>;
  elapsedMs: number;
}

export async function persistSeedChains(
  database: SeedDatabase,
  chains: readonly GeneratedSeedChain[],
  context: { seed: string; startedAt: number },
): Promise<SeedReport>;
```

If the schema barrel uses the generated snake-case export for a table rather than the camel-case name shown above, alias only at this import boundary (for example, `imovel_documento as imovelDocumento`) and leave the writer API unchanged.

**Insertion algorithm**

1. Insert or validate the synthetic CRIs before chain data:

   - `1, "1º CRI de SP", uf "SP", createdAt: new Date().toISOString(), updatedAt: new Date().toISOString()`
   - `2, "1º CRI de RJ", uf "RJ", createdAt: new Date().toISOString(), updatedAt: new Date().toISOString()`
   - `3, "1º CRI de MG", uf "MG", createdAt: new Date().toISOString(), updatedAt: new Date().toISOString()`

   Select the three rows back and compare ID/name/UF. Count only rows inserted by this run in `report.inserted.cris`.
2. Select `lancamento_tipo` IDs 1, 2, and 3 and validate their expected enum values before inserting any chains.
3. For every chain, choose `criId = (chain.index % 3) + 1` and perform inserts in this exact order:

   1. `documento`, mapping each filled documento by `topologyId`; set `tipo` from the topology document kind, `numero`, optional `data`, `numeroRaw` where available, and `cri_id`.
   2. `pessoa`, mapping only `{ nome }`. Explicitly do not spread a `FilledPessoa` object into the insert.
   3. `imovel`, using the filled name/denomination and a deterministic summary of area/location in `observacoes`, the round-robin `cri_id`, optional first chain person as `proprietario_id`, and `arquivado: 0`.
	   4. `lancamento`, resolving `documento_id` from the document map and `tipo_id` through the fixed lookup mapping. Track per-document sequential `numero_lancamento` starting at 1 (increment for each lancamento with the same documento_id). Map topology launch types deterministically to `forma` based on `TopologyLancamento.tipo`: `registro` → `"Registro"`, `averbacao` → `"Averbação"`, `inicio_matricula` → `"Início de Matrícula"`. Populate only schema-supported optional values.
	   5. `lancamento_pessoa`, synthesizing 1-3 deterministic junction rows per lancamento using the chain's pessoas with round-robin assignment. Set `papel` to `"transmitente"` or `"adquirente"` deterministically. Use `pessoa_id: null` plus `nomeVerbatim` when a lancamento has no associated person.
	   6. `origem`, resolving `lancamento_id`, optional `documento_id`, and `cri_id` (use the round-robin CRI). Set `tipo` from topology origem type, `numero` from topology origem number, and preserve deterministic `indice`.
   7. `origem_fim_cadeia`, resolving `origem_id` and mapping the topology end classification into the schema fields.
	   8. `imovel_documento`, after both maps exist; set `isDocumentoAtual: true` for the most recent imovel-documento link per topology, and `false` for others. Leave delete fields omitted.

4. Use Drizzle `.returning({ id: table.id })` for every entity whose ID is referenced later and store the result immediately in that entity’s topology-ID map. Throw if an expected returned ID or referenced topology ID is missing.
5. Keep insert values as explicit object literals. This prevents accidental writes of `cpfCnpj`, `tipo` from filled people, `deletedAt`, or unsupported topology fields.
6. Use the transaction/batch primitive supported by the existing API database adapter so a failed chain does not leave a partially inserted chain. Preserve dependency order even when batching equal-table rows.
7. Compute report counters from successful returned rows, not from requested input lengths. Compute `elapsedMs` from `performance.now() - context.startedAt`.

**Acceptance tests**

On a freshly migrated test database, persist a small mixed-shape batch and assert:

- `PRAGMA foreign_key_check` returns no rows;
- every expected table count matches the report;
- all soft-delete columns are `NULL` and every `imovel.arquivado` is `0`;
- only `pessoa.nome` is populated from filled-person PII;
- document/imovel CRIs rotate through 1, 2, and 3;
- `lancamento_tipo` references are limited to 1–3;
- a broken topology reference rejects without a partial chain.

```bash
pnpm -C packages/api db:migrate:local
pnpm --dir scripts/seed test -- seed.test.ts
```

This subtask is one persistence module plus the database-backed section of one test file and should fit within 15–20 implementation turns.

**Entrypoint**

import { db } from "../../packages/api/src/db";

## Subtask 4 — Complete replay, integrity, volume, and performance coverage

**Files**

- Complete `scripts/seed/__tests__/seed.test.ts`.
- Modify no production files unless a failing acceptance test exposes a T-202 defect.

**Test cases**

1. **Replay determinism:** create two freshly migrated isolated databases, run `runSeed({ count: 5, seed: "42" })` against each, query logical columns ordered by stable topology/insertion order, exclude auto-generated timestamps/elapsed time, and assert deep equality.
2. **Different-seed variation:** run the same count with another seed and assert that document numbers, person names, or topology relations differ.
3. **Default volume and weighted shapes:** generate/persist the default 50 chains and assert at least 50 imoveis and 500 lancamentos. Assert shape counters sum to 50. Test weighted threshold behavior separately on a large generated sample; do not require a 50-item run to equal exactly 5/30/15.
4. **Forced shape:** run a small batch for each of linear, branching, and merge and assert the report contains only the forced shape while all foreign keys remain valid.
5. **PII and deletion policy:** inspect the stored schema rows, assert person rows contain only the generated name among supported person fields, and assert all `deleted_at`/delete-operation values are `NULL`.
6. **Performance:** time the default 500-launch run and require `< 30_000 ms`. Give the test its own Vitest timeout slightly above 30 seconds and print the report if it fails.
7. **Report accuracy:** compare every report counter with `SELECT count(*)` for its table and ensure the printed/reported seed can replay the run.

Each database-backed case must start from an isolated migrated SQLite/D1 database. Do not share the developer’s normal local database between replay cases, and remove only test-owned temporary database files during teardown.

**Acceptance commands**

```bash
pnpm --dir scripts/seed test -- seed.test.ts
pnpm test:unit
pnpm -C packages/api db:migrate:local
pnpm seed -- --seed 42
```

For the final manual command, verify the report shows 50 chains, at least 50 imoveis, at least 500 lancamentos, a shape total of 50, and completion below 30 seconds. Then run the database adapter’s SQLite query path for `PRAGMA foreign_key_check`; it must return no rows.

This subtask is test-only in the expected case and should fit within 15–20 implementation turns.

## Risks and mitigations

- **D1 transaction support differs from a conventional SQLite driver.** Confirm the transaction or `batch` facility exposed by `packages/api/src/db` in Subtask 2 and keep the writer’s injected `SeedDatabase` type tied to that real export.
- **Schema export names may differ from table names.** Resolve this only in the schema import/alias block; do not spread naming differences through the writer.
- **Topology relations may include optional references.** Validate every topology-ID lookup and either persist the schema-supported nullable/verbatim representation or fail before inserting the dependent row.
- **Explicit CRI IDs can collide on a non-fresh database.** Validate existing rows and abort on mismatches; never update or delete existing CRIs implicitly.
- **Timestamps can break replay comparisons.** Determinism applies to logical seed content. Exclude database-managed timestamps and elapsed time from equality assertions.
- **Default runs can exceed CI time on slower hosts.** Insert rows in dependency-preserving groups/batches, avoid one database round-trip per lookup, and keep the explicit 30-second acceptance test.

## Definition of done

T-202 is complete when all four acceptance command groups pass, `pnpm seed` defaults to a reported random seed and 50 chains, `--seed 42` is replayable, forced and weighted shapes work, the default database contains at least 50 imoveis and 500 lancamentos, `PRAGMA foreign_key_check` is empty, no PII-only fields or soft-deleted rows are written, and the final report accurately reflects a run under 30 seconds.

The immediate implementation step is Subtask 1: add `seed-orchestrator.ts` and the pure deterministic/CLI tests before introducing database writes.

## Hermes independent verdict (post-Codex)

**Round-1 verdict: 2 MUST-FIX / 6 NICE / 0 DISAGREE — plan CONDITIONAL-APPROVE.**

### MUST-FIX

**M-1: `lancamento.numero_lancamento` UNIQUE constraint.** The `lancamento` table has `UNIQUE(documento_id, numero_lancamento)`. The seed writer MUST generate sequential per-document `numero_lancamento` values (1, 2, 3, ... per document) or the insert will fail. Subtask 2 step 3.4 must specify this.

**M-2: CRI `created_at` / `updated_at` columns.** The `cri` schema has `createdAt: text().notNull()` and `updatedAt: text().notNull()` with `$onUpdate`. The writer must provide explicit values when inserting CRIs (e.g., `new Date().toISOString()` for both). Without this the insert will fail.

### NICE

**N-1: Turbo pipeline.** The plan doesn't add `scripts/seed` to Turbo's `test:unit` pipeline. Currently `turbo run test:unit` requires `dependsOn: ["^build"]` per `turbo.json`; `scripts/seed` has no `build` task. Either remove the turbo dep or add a `build` script to `scripts/seed/package.json`. Without this, `pnpm test:unit` in CI may skip seed tests.

**N-2: Vitest filter syntax.** The acceptance command `pnpm --dir scripts/seed test -- seed.test.ts` uses `--` passthrough for vitest — verify that `vitest run seed.test.ts` (no `--`) is the correct form. The existing package.json has `"test": "vitest run"` so `pnpm test` runs all tests; filtering via `pnpm test -- -t "pattern"` may be needed.

**N-3: `origem.documento_id` cross-chain resolution.** The `TopologyOrigem.documentoId` may reference a documento from another chain. Subtask 2 should document: intra-chain refs resolve via the `Map<topologyId, dbId>`; cross-chain refs get `documento_id: null` (the column is nullable; `ON DELETE SET NULL`).

**N-4: `lancamento_pessoa` mapping gap.** The topology graph doesn't model which pessoas participate in which lancamentos — `TopologyGraph` has no `lancamento_pessoa` field. Implementation choices: (a) create 1-3 random `lancamento_pessoa` rows per chain using the chain's pessoas with deterministic roles (transmitente/adquirente); (b) skip entirely. Either is acceptable for seed purposes; document the choice.

**N-5: Transaction/batch API discovery.** The plan assumes `packages/api/src/db` exposes a transaction or batch API. The implementer MUST read the actual DB module first (not assume). If D1's Drizzle adapter doesn't support transactions, fall back to sequential inserts with FK-order guarantee.

**N-6: `imovel.observacoes` population.** The plan says "deterministic summary of area/location in `observacoes`." Good, but be explicit: use template literal like `"Área: ${areaTotal}ha, ${municipio}/${uf}"` so tests can assert on it.
